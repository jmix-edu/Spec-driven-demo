## Spec-Driven Workflow

### Order

Spec -> my review of the spec -> implementation -> Review -> Verify.

- Write the spec from my prompt, then stop and wait for my approval. Write no
  code before I approve the spec.
- Small one-off changes (a form default, a seed bean) need no spec: implement
  them directly and say what you did.

### Spec location

- Path: `specs/<NN_module>/<NN>-<slug>.spec.adoc`.
- Modules follow the course lessons: `01_foundations`, `02_security`,
  `03_files`, `04_deployment`, `05_addons`.
- If I don't give a path, derive the module from the topic and take the next
  free `<NN>` in that module.

### What you generate and what you don't

- Standard CRUD list/detail views and Liquibase changelogs are generated by Jmix
  Studio, not by you. Ask me to generate them in Studio.
- If you are unsure how a standard Jmix artifact should look, ask me for a
  Studio sample and repeat it.

### Gates

- Gate 1 and Gate 2: as the Jmix toolkit (`jmix` skill) says.
- Gate 3: don't walk the browser yourself. End with a short checklist of what I
  should check in the browser.
- Tests only where behaviour is hard to check by hand: security, business rules.
- Run builds and tests in the foreground and show their result.

### Safety

- Never run global cleanup commands: `docker system prune`,
  `docker volume prune`, `docker image prune`, `rm -rf` outside the project.
  Remove only what you created, by name.
- Never print environment variables, secrets, or the output of
  `docker compose config`.

### Git

- Don't commit. I commit after each step.
