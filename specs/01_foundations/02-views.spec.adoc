:toc: macro
:status: approved

== Goal

CRUD screens for the data model from `01-data-model.spec.adoc`: Building, Floor, Room,
Desk, Amenity, Booking. The scaffold is generated by Jmix Studio. This spec fixes
*which* screens exist, the canon rules every screen follows, the title and menu keys,
and how the Studio output is checked against the canon.

== Scope

=== In scope

* List, detail and lookup views for the six entities (see <<screens>>).
* Composition editing: floors inside a building, rooms and desks inside a floor.
* Many-to-many Room ↔ Amenity as an inline grid in the room detail view.
* Title and menu message keys, menu items.
* Fetch plans of these views: every displayed reference is fetched by the view's loader.

=== Out of scope

* Security: view/menu policies and roles (`02_security`). Until then the screens are
  reachable only by users with `system-full-access` (e.g. `admin`).
* Booking rules: slot check, start < end, "exactly one of room / desk", status
  transitions (a later spec).
* Custom UI: calendars, floor plans, dashboards, styling, custom renderers.
* "My bookings" filtering. (Prefilling the booking form — current user, next full hour
  for one hour — was added later as a one-off change in `BookingDetailView`.)
* Localization beyond `en`.
* UI tests — the views carry no business logic (see CLAUDE.md, "tests only where
  behaviour is hard to check by hand").

No `Floor.list`, `Room.list`, `Desk.list`: floors, rooms and desks are owned by their
building and floor and are edited only inside the aggregate. `Room.lookup` and
`Desk.lookup` are pick-only (no create/edit/remove).

Menu (inside the existing `application` menu), in this order: Buildings, Amenities,
Bookings, Users.

== Canon rules

These hold for every screen in this spec, Studio output included.

. *`@ManyToOne` reference* → `entityPicker` with the wizard's standard actions
  `entity_lookup` + `entity_clear`. The lookup opens the entity's lookup/list view.
. *Composition back reference* (`Floor.building`, `Room.floor`, `Desk.floor`) → not on
  the child form; Jmix sets it from the parent grid.
. *Enum* → a dropdown (`select`), bound to the property only; no `entityComboBox`.
. *Composition collection* → a property-bound `<collection property="…"/>` (no loader,
  no query), parent fetch plan includes the property, grid with `list_create` /
  `list_edit` in `openMode = DIALOG` and `list_remove`, each with a visible button.
. *Many-to-many* (`Room.amenities`) → an inline property-bound grid with `list_add`
  (opens `Amenity.list` as lookup) and `list_exclude`, each with a visible button.
  Excluding removes the link only, never the amenity.
. *Technical fields hidden*: `id` and `version` appear on no form, grid or filter
  column list.
. *Fetch plans*: every reference shown in a grid column or a form field is in the
  loader's fetch plan with `fetchPlan="_instance_name"` — no lazy loading per row.
. *Integer property* → `integerField`, not `textField`.
. *Titles and buttons* come from message keys; no hard-coded text.

== Message keys

Follow the Studio convention for new views — view-package group, lower-camel view
name. The generated `User` views keep their own `UserListView.title` style; they are
not renamed.

[cols="3,2"]
|===
|Key |Value

|`com.company.booking.view.building/buildingListView.title` |Buildings
|`com.company.booking.view.building/buildingDetailView.title` |Building
|`com.company.booking.view.floor/floorDetailView.title` |Floor
|`com.company.booking.view.room/roomDetailView.title` |Room
|`com.company.booking.view.room/roomLookupView.title` |Rooms
|`com.company.booking.view.desk/deskDetailView.title` |Desk
|`com.company.booking.view.desk/deskLookupView.title` |Desks
|`com.company.booking.view.amenity/amenityListView.title` |Amenities
|`com.company.booking.view.amenity/amenityDetailView.title` |Amenity
|`com.company.booking.view.booking/bookingListView.title` |Bookings
|`com.company.booking.view.booking/bookingDetailView.title` |Booking
|===

Menu items reuse the list-view title keys with a full `msg://<group>/<key>` reference,
as Studio generates them. Field labels and grid headers come from the entity keys
added in `01-data-model`.

Studio has already generated the scaffold (`view/{building,floor,room,desk,amenity,booking}`).
Reviewed against the rules above:

|===
|Where |Deviation |Fix by

 wrong) → `roomLookupView.title`

 with `_instance_name`

|Order is Users, Bookings, Buildings, Amenities → Buildings, Amenities, Bookings, Users
|me

|`floor-detail-view.xml` (`number`), `room-detail-view.xml` (`capacity`)
|`textField` for an `Integer` property → `integerField`
|me

|`room-lookup-view.xml`, `desk-lookup-view.xml`
|Same-named rooms/desks are indistinguishable → fetch `floor` and `floor.building`
 (`_instance_name`), add `floor` and `floor.building` columns, order by building name,
 floor number, room name / desk code

Everything else matches the canon: composition grids with DIALOG create/edit, M2M
grid with add/exclude, back references hidden, `select` for `status`, pickers with
`entity_lookup` / `entity_clear`, no `id` / `version` anywhere.

Only these targeted edits are mine; the screens are not regenerated or rewritten by
hand. If a fix turns out to need more than a small edit, I stop and ask for a Studio
sample.

== Acceptance criteria

. Every view in <<screens>> exists with that id; no `Floor.list`, `Room.list`,
  `Desk.list`.
. The menu has exactly Buildings, Amenities, Bookings, Users in that order, and each
  opens its list.
. Every rule in "Canon rules" holds in every descriptor of this spec.
. Every `msg://` reference in these descriptors and in `menu.xml` resolves in
  `messages_en.properties`; no `roomLoolkupView` left.
. Booking list and detail fetch `user`, `room` and `desk` in the loader.
. Gate 1: JetBrains inspection reports no errors or Jmix warnings on every descriptor
  and controller of this spec and on `menu.xml`.
. Gate 2: `./gradlew --no-daemon clean test` is green.
. Gate 3 (you, in the browser): the checklist below passes.

=== Browser checklist (Gate 3)

. Menu shows Buildings, Amenities, Bookings, Users.
. Amenities: create "Projector", "Whiteboard"; edit one; the list shows name and
  description only.
. Buildings → create a building → in its floors grid add a floor (dialog) → in the
  floor's rooms grid add a room with capacity, in its amenities grid add "Projector"
  (lookup), then exclude and re-add it → add a desk → save everything; reopen and see
  it all persisted.
. Floor number and room capacity accept digits only. Room form: no floor field; floor form: no building field; no form shows ID or
  Version.
. Bookings → create: pick a user, a room via the lookup dialog (only pick, no
  create/edit buttons; floor and building columns filled), start/end; status is a dropdown preset to Confirmed; save; the
  list shows user, room and status.
. Same with a desk instead of a room.
. Delete the amenity that is linked to a room → database error (expected per
  `01-data-model`); delete a room with no bookings → works.

== Decisions

. Integer properties use `integerField`.
. Room and desk lookups show floor and building now.
. Menu order: Buildings, Amenities, Bookings, Users.
