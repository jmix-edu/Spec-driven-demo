= 03.01 — Floor plans
:toc: macro
:status: approved

toc::[]

== Goal

Each floor can have a plan — an image of the floor layout. The office manager uploads it
in the floor form. An employee filling in a booking sees the plan of the chosen room's or
desk's floor right in the booking form and can download it. Only PNG and JPEG, at most
10 MB.

== What Jmix offers (as found in 3.0.3, not assumed)

[cols="2,5"]
|===
|File reference |`io.jmix.core.FileRef` attribute on the entity, `varchar(1024)` column; the
 JPA converter applies automatically (toolkit, `jmix-create-entity`).
|Storage |`jmix-localfs-starter` is already in `build.gradle`: local file system storage.
|Upload |`<fileStorageUploadField>` binds to a `FileRef` property (`dataContainer`,
 `property`) and has `acceptedFileTypes`, `maxFileSize`, `fileTooBigText`,
 `incorrectFileTypeText`, `fileStoragePutMode`.
|Display |The layout `<image>` (`JmixImage`) binds to a `FileRef` property through
 `dataContainer` / `property` and renders the stored file.
|Download |`io.jmix.flowui.download.Downloader.download(FileRef)`.
|===

== Where the files live

[cols="2,5"]
|===
|Root |`jmix.localfs.storage-dir` — not set, so the default applies:
 `<jmix.core.work-dir>/filestorage`, and `jmix.core.work-dir = ${user.dir}/.jmix/work`.

|dev |`<project root>/.jmix/work/filestorage/` (IntelliJ and `bootRun` run with the project
 root as working directory). Already git-ignored through `.jmix`.

|Layout |`<root>/<yyyy>/<MM>/<dd>/<uuid>.<ext>` — the date of upload and a random name; the
 original file name is kept in the `FileRef` (database), not on disk.

|Tests |Same `.jmix/work/filestorage` (same working directory). The tests of this spec store
 no files (see "Tests").

|Container |`/app/.jmix/work/filestorage` — already on the named volume `booking-app-work`
 from Lesson 4; nothing to change in this step.
|===

No new property: the default is spelled out here and in the README instead of being
repeated in `application-dev.properties`.

== Design

=== Model

`Floor.plan` — `FileRef`, column `PLAN varchar(1024)`, optional. Message key
`com.company.booking.entity/Floor.plan=Plan`.

Changelog: generated by *you in Studio* (`addColumn` on `FLOOR`), reviewed by me
(CLAUDE.md).

=== Floor form (`floor-detail-view.xml`)

A targeted edit of the Studio descriptor, like the Lesson 1 canon fixes:

* `<fileStorageUploadField id="planField" property="plan">` in the form, with
  `acceptedFileTypes` = `image/png,image/jpeg,.png,.jpg,.jpeg`,
  `maxFileSize` = `10485760` (10 MB),
  `fileTooBigText` / `incorrectFileTypeText` from message keys,
  `clearButtonVisible` so a plan can be removed.
* A small preview `<image>` bound to `plan` under the form, so the manager sees what was
  uploaded.

=== Data-level rule: PNG/JPEG only

The upload field's checks run in the browser; a save through any other path would bypass
them. A `Floor` saving listener (`EntitySavingEvent<Floor>`) rejects a plan whose file name
does not end in `.png`, `.jpg` or `.jpeg` (case-insensitive) with a clear message. This is
a check of the *declared* type: content sniffing is out of scope.

The 10 MB limit is enforced by the upload field; the storage-wide limit
(`jmix.localfs.max-file-size`, default 100 MB) stays as it is.

=== Booking form (`booking-detail-view.xml` + `BookingDetailView`)

* A "Floor plan" section under the form: an `<image>` bound to a separate instance
  container `floorPlanDc` (`Floor`, fetch plan `name`, `plan`) and a "Download plan" button.
* `floorPlanDc` has no loader: the controller loads *the floor of the selected room or desk*
  with `DataManager` (a query by the place's id) and sets it as the container's item:
  ** when the form opens (existing booking),
  ** whenever `room` or `desk` changes (`ItemPropertyChangeEvent` of `bookingDc`).
* The picked room/desk from the lookup carries only its instance name, so the floor and
  its plan are always loaded by the query, never read through `room.floor`.
* No place chosen, or the floor has no plan → the image is hidden and a short text says
  so; the download button is disabled.
* Download → `Downloader.download(plan)` — the original file name is preserved.
* Works the same in read-only mode (office manager opening a booking).

=== Message keys

Floor view: `planField` errors (`fileTooBig`, `incorrectFileType`). Booking view: section
title "Floor plan", "No floor plan for the selected place", "Download plan". The
listener's rejection message: group `com.company.booking.listener`. All `en`.

== Tests

The type rule is a business rule (CLAUDE.md) → `FloorPlanValidationTest`, integration,
through `DataManager.save()`, with `FileRef`s created in memory (`new FileRef(storage,
path, fileName)`) — no file is stored:

. `plan.png`, `PLAN.JPG`, `plan.jpeg` → saved.
. `plan.pdf`, `plan` (no extension), `plan.png.exe` → rejected with the message.
. No plan → saved.

Upload, preview, the booking-form section and download are UI behaviour → browser
checklist (Gate 3).

== Scope

=== In scope

* `Floor.plan`, its changelog (Studio), message keys.
* Upload field and preview in the floor form; PNG/JPEG and 10 MB limits.
* The `Floor` saving listener for the type rule; `FloorPlanValidationTest`.
* Floor-plan section with download in the booking form.
* Documenting where files live (this spec, README line).

=== Out of scope

* Roles: no role changes. Today's roles already cover it — Office Manager has `MODIFY *`
  on `Floor`, Employee `VIEW *`; if implementation finds a gap, it is reported, not fixed
  here.
* The container (volume already exists since Lesson 4).
* Cleaning up orphaned files: a replaced or removed plan, a cancelled upload
  (`fileStoragePutMode` default stores on upload) and floors deleted by the database
  cascade leave their files in storage.
* Content-type sniffing, virus scanning, image resizing/thumbnails, several plans per
  floor, marking the room or desk on the plan.
* Other file storages (S3 etc.).

== Acceptance criteria

. `Floor.plan` exists as `FileRef`; the Studio changelog adds `PLAN varchar(1024)`
  (reviewed).
. The floor form accepts a PNG/JPEG up to 10 MB, refuses other types and larger files with
  readable messages, shows a preview, and can clear the plan.
. Saving a floor whose plan is not `.png/.jpg/.jpeg` fails through any path
  (`FloorPlanValidationTest` green).
. The booking form shows the plan of the selected room's or desk's floor, updates when the
  place changes, hides it when there is none, and downloads it with its original name.
. Files land in `<project root>/.jmix/work/filestorage/<yyyy>/<MM>/<dd>/` in dev.
. Gate 1: inspection on every Java file; mechanical descriptor checks on both descriptors
  (`msg://` keys resolve, component ids and containers match).
. Gate 2: `./gradlew --no-daemon clean test` green.

=== Browser checklist (Gate 3)

. *maria*: Buildings → Head Office → 1st floor → upload a PNG → preview appears; save.
  Upload a PDF → refused; a 12 MB JPEG → refused.
. Check `.jmix/work/filestorage/<today>/` → one `<uuid>.png`.
. *emma*: new booking → pick room Aurora → the 1st-floor plan appears; switch to a desk on
  the 2nd floor (no plan) → "No floor plan…", download disabled; back to Aurora → Download
  plan → the original file name.
. *maria*: open emma's booking (read-only) → the plan is shown and downloadable.
. *maria*: clear the plan, save → the booking form shows "No floor plan…".

== Decisions

. 10 MB enforced by the upload field only; the storage-wide limit stays at 100 MB.
. Type rule checks the file name (`.png`, `.jpg`, `.jpeg`), not the content.
. The preview in the floor form stays.
